Nine small programs, each validating one subsystem of a freshly assembled board.
Flash one, confirm the hardware works, move on. They are also the shortest honest
answer to "how do I use this driver?"

| Example | What it proves |
|---|---|
| `01_blink` | Onboard and carrier LED — boots and is alive |
| `02_audio_tone` | 440 Hz sine on the output jacks — codec and SAI path |
| `03_midi_mono_sine` | MIDI IN to a monophonic sine voice with a short ADSR |
| `04_adc_1ch` | One channel of the external ADS114S08 to serial |
| `05_adc_scan` | Full 24-channel scan via `rodeo::RodeoAdc` |
| `06_poly_synth` | 6-voice poly subtractive synth, 10 live pots — the first musical demo |
| `07_encoder_scan` | Hub scan via `rodeo::RodeoEncoders`, shown on the OLED |
| `08_oled_i2c` | SSD1309 128×64 smoke test, I²C at `0x3C` |
| `09_poly_synth_oled` | `06` plus the OLED: knob popups and a live output scope |

```sh
cd rodeo-sdk/examples/05_adc_scan
make && make program-dfu
```

## Suggested order on a new board

`01` first — if the LED does not blink, nothing else is worth trying. Then `02` for
the audio path, `04` before `05` so a single channel is proven before the full scan,
and `08` before `07` because the encoder example draws to the display.

:::note[What has actually been run]
`04_adc_1ch` and `05_adc_scan` are bench-confirmed on real hardware, and
`07_encoder_scan` proved the hub's I²C pass-through and bus pull-ups at the hub's
first bring-up. The others carry a stated pass criterion but are not individually
attested here — treat them as written and expected to work rather than witnessed.
:::
