The firmware side of the Rodeo platform: the drivers that read the motherboard's
control surface, a template to start an instrument from, and nine bring-up examples
that validate a freshly assembled board one subsystem at a time.

It is built on **libDaisy** and **DaisySP**, so you are writing an Electrosmith Daisy
program — `rodeo-sdk` adds what the Daisy cannot do on its own: twenty-four extra
16-bit analog channels, the I²C encoder hubs, and a display transport fast enough to
leave headroom for audio.

:::note[Version 0.1.0, and 0.x on purpose]
Two instruments in, the shape is clear but the seams are not all settled.
`common/version.h` carries the changelog and names what still stands between this and
a 1.0. Apps can refuse to build against an SDK that is too old:

```cpp
static_assert(RODEO_SDK_AT_LEAST(0, 1, 0), "this app needs a newer SDK");
```
:::

## The two layers

Every driver is split the same way, and it is worth knowing which one you want.

**Layer 1** is one chip. `ads114s08.{h,cpp}` talks to a single ADS114S08 over SPI;
`encoder_hub.{h,cpp}` talks to one STM32C0 hub over I²C. Use these if you are doing
something unusual.

**Layer 2** is the board. `rodeo_adc.{h,cpp}` presents all twenty-four analog channels
as one pipelined scanner across both chips; `rodeo_encoders.{h,cpp}` presents up to
four hubs as one flat list of encoders. This is what instrument code should use.

## The pure-logic headers are the point

`adc_convert.h`, `pot_ui.h`, `rodeo_dsp.h`, `rodeo_scope.h` and `rodeo_screen.h`
contain no libDaisy and no hardware. They compile on your laptop, `common/tests/`
exercises them there with GoogleTest, and the firmware calls *those* functions rather
than a second implementation that drifts.

Anything that is just maths and state belongs there — which means most of the logic
in an instrument can be tested without a board plugged in.
