title: Pure-logic headers

---

Six headers contain no libDaisy and no hardware. They compile on your laptop,
`common/tests/` exercises them there, and the firmware calls **these** functions
rather than a parallel implementation that drifts from the tested one.

| Header | What is in it |
|---|---|
| [`adc_convert.h`](/sdk/reference/api/adc-convert/) | The ADC value pipeline, and `PotSpan` knob-travel calibration |
| [`pot_ui.h`](/sdk/reference/api/pot-ui/) | Panel logic: stepped pots, and "which knob is the user moving?" |
| [`rodeo_dsp.h`](/sdk/reference/api/rodeo-dsp/) | `Smoother`, `OnePole`, `DcBlocker`, `Lfo`, `Rng` |
| [`rodeo_scope.h`](/sdk/reference/api/rodeo-scope/) | A triggered, normalised waveform for a small display |
| [`rodeo_screen.h`](/sdk/reference/api/rodeo-screen/) | 128×64 primitives: title bar, list rows, scroll bar |
| [`sat_frame.h`](/sdk/reference/api/sat-frame/) | The satellite chain's wire format: frames, slots, CRC, discovery, commands |

`sat_frame.h` is plain C, because the satellites include it too: the chain's two
ends share one definition of every byte, and the host tests play both parts, down
to a simulated ring of satellites.

Each links to its page in the API reference, which is generated from the header
itself.

## Why this matters

Most of what makes an instrument feel right is not hardware access — it is smoothing,
stepping, hysteresis and display state. Keeping that in host-testable headers means
it can be exercised without a board, and a change that breaks a knob's behaviour
fails a test rather than being discovered by ear.

```sh
cd rodeo-sdk/common/tests
make && ./build/tests
```

The rule the SDK follows: **anything that is just maths and state belongs here.**

## Seeing screens without hardware

`tools/screens/` renders an instrument's real OLED screens on your laptop, using the
same `rodeo_screen.h` primitives the firmware uses. The screen you are looking at is
drawn by the same code that will draw it on the panel.
